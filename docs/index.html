Stop Asking One AI.
Start Running a Debate.

What happens when 33 AI expert personas argue about your architecture decision — and why the disagreements are the point.

21 min read

We asked Claude whether a fintech startup should use microservices. It gave us a thoughtful, balanced answer: "it depends on your team size, scale requirements, and compliance needs." Reasonable. Polite. Useless.

We asked the same question to Parliagent. Thirty-two AI expert personas argued for 24 seconds. The result: 94% opposed microservices, 33 specific warnings about PCI DSS violations and regulatory audit fragmentation, and this from NietzscheSeat:

NietzscheSeat oppose · confidence 4/5
"The microservices movement is largely driven by engineering ressentiment — developers who feel inadequate building simple things well, so they create complexity to justify their existence."

That's the difference between asking one AI and running a debate. The single agent hedges. The parliament takes positions, disagrees, warns you about things you didn't ask about, and occasionally says something so uncomfortable it reframes the entire question.

Ask an LLM a hard architecture question and you'll get a confident, well-structured answer. It will sound authoritative. It will cite best practices. It will have a reassuring tone that makes you want to nod along. The problem is, it's one voice. One set of biases, one set of blind spots, one set of priors baked into a single forward pass. The dissenting voices, the uncomfortable warnings, the "yes, but what about regulatory compliance?" objections? Buried in hedging language, if they surface at all.

This is the echo chamber of one. And it's the default mode for how most people use AI today.

We built Parliagent to fix this. It's a multi-agent deliberation engine that runs a structured parliamentary debate among expert personas — with disagreement tracking, minority reports, and budget controls. One function call. Multiple perspectives. Structured dissent.

To write this article, we did something recursive: we asked Parliagent how to write about itself. Then we asked it to review what it wrote. Then it flagged its own circular reasoning. More on that later.

Why Single-Agent Falls Short

Anthropic's engineering team recently documented a key failure mode they encountered while building long-running coding agents: self-evaluation doesn't work.

"When asked to evaluate work they've produced, agents tend to respond by confidently praising the work — even when, to a human observer, the quality is obviously mediocre."

Their solution was to separate the generator from the evaluator — a distinct agent whose job is to be skeptical. This works for code, where there are verifiable outcomes. But what about decisions that don't have unit tests? Architecture tradeoffs. Security design. Strategic pivots. Planning under uncertainty.

For these problems, you don't just need a skeptic — you need a parliament. Multiple experts with different domains, different priors, different blind spots, structurally incentivized to disagree.

Here's what the data shows. We benchmarked Parliagent against a single-agent baseline across 10 prompts spanning coding, planning, writing, strategy, security, and analysis:

The baseline produces zero disagreements. Not because there's nothing to disagree about — because there's no one to disagree with. A single agent asked about security will mention security concerns. But it won't have SecurityPrivacySeat specifically raising PCI DSS violations while KahnemanSeat points out that you're anchoring on a microservices hype cycle.

The disagreements are the value. Micro mode adds 3.4 disagreements at just 1.6x the cost and 2 seconds more latency. Fast mode surfaces 10.6 disagreements — three times more conflict for six times the cost. That's not overhead. That's surface area for the things you'd otherwise miss.

The Architecture

Parliagent is a TypeScript library (npm install parliagent) with a single entry point:

import { debate } from "parliagent";

const response = await debate({
  prompt: "Should we use microservices or a monolith?",
  mode: "fast",
  taskType: "strategy",
});

console.log(response.finalAnswer);       // synthesized answer
console.log(response.decisionType);      // "consensus" | "majority" | "split" | "uncertain"
console.log(response.minorityReport);    // dissenting views
console.log(response.warnings);          // safety/security flags

Behind that one-liner, here's what happens:

graph LR A["debate(request)"] --> B["Speaker"] B --> C["Safety Check"] C --> D["Task Classification"] D --> E["Seat Routing"] E --> F["Parallel Seat Calls"] F --> G["Convergence Check"] G -->|"not converged"| F G -->|"converged / round limit"| H["Synthesis"] H --> I["ParliagentResponse"]

1. The Speaker

The Speaker is the neutral chair — it never takes a substantive position. It routes the question to the right seats, manages debate rounds, and synthesizes the final answer from member contributions. Think of it as the procedural backbone.

2. Seat Routing

When a request arrives, the system classifies the task type (coding, planning, strategy, analysis, ethics, writing, general) using keyword scoring, then selects a chamber of seats appropriate for the mode:

// Simplified from src/core/routing.ts
export function classifyTask(prompt: string): TaskType {
  const signals: Record<TaskType, string[]> = {
    coding: ["code", "function", "implement", "debug", "api", ...],
    strategy: ["strategy", "competitive", "market", "pricing", ...],
    ethics: ["ethical", "bias", "fairness", "privacy", ...],
    // ...
  };
  // Score each type by keyword hits, return the best match
}

The routing is deliberately rule-based (not LLM-powered) because it runs on every request and needs to be fast, deterministic, and inspectable. You can preview routing without spending a token:

$ parliagent inspect "How to handle API key rotation?" --mode fast

Selected Chamber:
  • OpenAISeat — Strongest OpenAI-family generalist representative
  • DijkstraSeat — Correctness, structure, anti-sloppiness
  • SecurityPrivacySeat — Adversaries, misuse, trust boundaries
  
Routing Reason:
  Task classified as "coding". Security seat priority upgraded.

3. The 33 Seats

Each seat has a persona with a system prompt, domain expertise, strengths, blind spots, and a speaking style. They're not random — they're chosen to create productive tension:

CategorySeatsWhat They Bring
Model RepsOpenAISeat, ClaudeSeat, GeminiSeatCross-family model diversity (4 provider backends)
ComputingDijkstra, Knuth, Shannon, TuringCorrectness, algorithms, information theory
PhilosophyAristotle, Kant, NietzscheEthics, duty, uncomfortable truths
PsychologyKahneman, Jung, CognitiveSciBias detection, cognitive framing
SecuritySecurityPrivacy, DistributedSystemsAttack surfaces, failure modes
ProductProductStrategy, Operator, DesignCommUser value, execution realism
Law & EthicsLawGovernance, EthicsHumanImpact, CitizenPragmatistRegulatory, fairness, practical impact

Seats speak in parallel. Each produces a structured JSON statement with a stance (support / mixed / oppose / uncertain), claims, objections, confidence level, and optional warnings. In subsequent rounds, they read each other's positions and can shift — or dig in.

4. Convergence

After each round, the system computes agreement ratios, clusters distinct claims using Jaccard similarity, counts objections, and decides whether to stop:

// Simplified from src/core/convergence.ts
if (blockingWarning && agreementRatio < 0.5) {
  return { shouldStop: true, reason: "blocking_warning" };
}
if (agreementRatio >= targetAgreementRatio && objectionCount <= 1) {
  return { shouldStop: true, reason: "converged" };
}
if (distinctViewCount <= 1 && objectionCount === 0) {
  return { shouldStop: true, reason: "converged" };
}
if (currentRound >= maxRounds) {
  return { shouldStop: true, reason: "round_limit" };
}

An important design decision: the debate stays in English internally, even when the user requests output in another language. English is where LLM reasoning is strongest. Only the final synthesis step renders in the target language (outputLanguage: "zh"). This means a Chinese-speaking user gets the benefit of English-language deliberation without the reasoning quality loss.

5. Synthesis

The Speaker reads all seat statements, disagreements, and warnings, then produces a synthesis that reflects the actual state of the debate — including dissent. If the decision type is split or uncertain, the response says so. It doesn't paper over disagreement with false confidence.

The verdict: start with a monolith. 30 out of 32 speaking seats opposed microservices, 2 were mixed, 0 supported them. That's 94% agreement — a rare near-consensus in a system designed to surface disagreement.

But the number that matters isn't the vote count. It's why they opposed, and how differently each seat framed the same conclusion. Here are six highlights from the debate transcript:

DijkstraSeat oppose · confidence 5/5
"A startup should begin with a monolith. Microservices introduce distributed system complexity that will overwhelm a small team before they understand their domain boundaries."
⚠ Financial systems require strong consistency guarantees — distributed transactions across microservices introduce significant complexity in maintaining data integrity for regulatory compliance.
SecurityPrivacySeat oppose · confidence 4/5
"Microservices exponentially increase attack surface with multiple network boundaries, API endpoints, and inter-service authentication points that can be compromised."
⚠ Microservices architecture could violate PCI DSS requirements around network segmentation and data flow monitoring if not implemented with enterprise-grade controls.
KahnemanSeat oppose · confidence 4/5
"A startup should begin with a monolith due to systematic overconfidence in microservices benefits and underestimation of complexity costs. The planning fallacy suggests microservices will take longer and cost more than anticipated."
⚠ The availability heuristic makes recent successful microservices stories more salient than the base rate of startups that failed due to premature architectural complexity.
LawGovernanceSeat oppose · confidence 4/5
"Regulatory compliance requires clear audit trails and data lineage — microservices create distributed transaction logs that complicate regulatory reporting and make it harder to demonstrate compliance during examinations."
FeynmanSeat oppose · confidence 4/5
"You don't yet know where the real boundaries in your system should be — premature microservice splits will force you into awkward data flows and make simple changes require coordinating multiple services."
NietzscheSeat oppose · confidence 4/5
"This question reveals the herd's obsession with architectural fashion over fundamental values. The microservices movement is largely driven by engineering ressentiment — developers who feel inadequate building simple things well, so they create complexity to justify their existence and salaries."

You saw this quote in the opening. Here's why it matters beyond shock value: NietzscheSeat reframed a technical architecture question as a psychological one. No other seat thought to question the motivation behind the question itself. That's not something you get from a single agent, no matter how good — it requires a persona whose entire job is to challenge the premise.

View the minority report

Even in a 94% consensus, two seats held back:

OpenAISeat mixed · confidence 4/5
"Both microservices and monoliths have distinct advantages; the choice depends on the startup's specific needs and resources. Microservices offer scalability and flexibility. Monolithic architectures can lead to faster initial development."
KantSeat mixed · confidence 4/5
"The choice must be determined by which architecture better enables the startup to treat its duties to customers, regulators, and society as categorical imperatives, not mere technical preferences."

The minority report exists because Parliagent never suppresses dissent. When the decision type isn't consensus, minority voices are surfaced explicitly — not buried in a paragraph of hedging.

Micro mode is the sweet spot for everyday use — it costs a penny, takes 16 seconds, and still surfaces 3+ disagreements on average. Fast mode is what we default for plan and review commands, where thoroughness matters more than speed.

We're being honest about balanced mode: it has diminishing returns. It costs 13.3x baseline but only produces 1.7x more disagreements than fast. Almost everything resolves as "uncertain" (9 out of 10 runs). More seats don't automatically mean more clarity — they mean more perspectives, which can fragment rather than converge. We recommend fast for most use cases and reserve balanced for genuinely high-stakes decisions.

A caveat our own parliament demanded we include: These benchmarks measure disagreement volume (how many objections are raised), not decision quality (whether the final answer is actually better). We don't yet have ground-truth validation comparing Parliagent decisions against outcomes or human expert panels. Ten prompts across six categories is enough to calibrate defaults, not enough to prove systematic superiority. We're being upfront about this because the parliament literally told us to — KahnemanSeat called it "measuring activity rather than accuracy."

Full Parliament at $1.50 per run is a special-purpose tool. You'd use it the way you'd schedule a board meeting — not for every question, but for the ones where you need every disciplinary angle covered.

What We Got Wrong (and What We're Honest About)

This section matters more than the architecture section. If we're going to ask you to trust a system that claims to surface hidden disagreements, we should surface our own.

Convergence rarely triggers

In 30 parliament runs across our benchmark suite, only 1 reached the convergence threshold early. The other 29 hit the round limit. This means either our convergence thresholds are too strict, or these debates genuinely don't converge when you have personas with different priors.

We think it's the latter — and it's by design. Parliagent is built to surface structured disagreement, not to manufacture premature consensus. The value is in the disagreement records and minority reports, not in everyone agreeing.

Writing tasks don't benefit from debate

A writing prompt in micro mode reached consensus in one round with zero disagreements. Even in fast mode, writing produced only 5 disagreements — the lowest of any category. This confirms what the SKILL.md explicitly warns: "The task is pure writing or drafting — debate adds nothing."

If your question has a single good answer, don't convene a parliament. Just answer it.

Four providers, all tested

Parliagent ships adapters for four LLM providers. All four are live-validated end-to-end against real API endpoints — individually and in federated/supreme combinations:

ProviderStatusValidated Modes
AnthropicLive-validated + benchmarkedSingle, federated, supreme, full parliament
OpenAILive-validatedSingle, federated (with Anthropic)
Google/GeminiLive-validatedSingle
FLOCKLive-validatedSingle, federated (with Anthropic), supreme

FLOCK deserves a note: it uses an OpenAI-compatible API format with x-litellm-api-key header auth, which means any OpenAI-compatible endpoint can plug in through the same adapter. You specify your model explicitly via FLOCK_MODEL — there's no hardcoded default, which keeps it genuinely provider-agnostic.

The federated execution profile — where OpenAISeat runs on OpenAI, ClaudeSeat runs on Anthropic, and other seats use whichever provider is primary — has been validated with both Anthropic+OpenAI and FLOCK+Anthropic combinations. We can confirm that cross-provider debates work; whether they produce meaningfully different disagreements than single-provider runs is a question we're still investigating.

Security detection is coarse

The auto-upgrade from micro to fast for security-sensitive prompts uses keyword matching. It catches "auth," "credentials," and "PCI," but it won't catch a subtle security implication buried in a business logic description. This is a limitation we intend to improve.

We used Parliagent to write this article. Then we used Parliagent to review this article. The review was brutal.

"This is a technically impressive article with a compelling core insight about structured disagreement, but it's trapped between being product documentation and paradigm manifesto — it needs to pick one lane and commit fully."

Individual seats were even more pointed:

KahnemanSeat mixed · confidence 4/5
"The article demonstrates genuine innovation but suffers from overconfidence in limited benchmarks. Measuring disagreement counts without tracking decision quality could lead to systematically worse decisions disguised as thoroughness."
ShannonSeat mixed · confidence 4/5
"The core insight about structured disagreement is mathematically elegant, but the execution obscures rather than amplifies this signal. The article has a signal-to-noise ratio problem."
NietzscheSeat mixed · confidence 4/5

The circularity problem: "Using multi-agent deliberation to evaluate multi-agent deliberation invalidates core claims without resolution." — flagged by 5 separate seats across both reviews.

This is the uncomfortable truth at the center of the project: we can't use Parliagent to prove Parliagent works. The tool can surface disagreements, flag risks, and force you to consider perspectives you hadn't thought of. But it can't be its own ground truth. That requires external validation — human expert panels, outcome tracking, controlled experiments — which we haven't done yet.

We're including all of this — the parliament's critique of itself, unedited — because hiding it would prove exactly the self-leniency problem the system is designed to solve. If 33 seats tell you the article has problems, and you publish the article anyway without mentioning what they said, you've defeated the purpose.

When to Use It (and When Not To)

Parliagent ships with a SKILL.md that AI agents can read directly. Here's the human version of the decision tree:

graph TD A["Is the question trivial or factual?"] -->|"Yes"| B["Don't call Parliagent"] A -->|"No"| C["Does it involve security/auth/credentials?"] C -->|"Yes"| D["mode: fast, taskType: coding"] C -->|"No"| E["Is it a plan/roadmap question?"] E -->|"Yes"| F["mode: fast, answerMode: plan"] E -->|"No"| G["Is it a review or risk assessment?"] G -->|"Yes"| H["mode: fast, answerMode: review"] G -->|"No"| I["Is it high-stakes/multi-disciplinary?"] I -->|"Yes"| J["mode: balanced or fullParliagent"] I -->|"No"| K["mode: micro"]

The key principle: match the cost to the stakes. A penny for a quick take. Four cents for a thorough review. A dollar fifty for a full parliament. Zero cents for a question that doesn't need debate.

Or from code:

import { debate } from "parliagent";

const result = await debate({
  prompt: "Should we use Redis or Memcached for our session store?",
  mode: "fast",
  taskType: "coding",
});

if (result.decisionType === "split" || result.decisionType === "uncertain") {
  // Parliament couldn't converge — surface both sides
  console.log("No consensus:", result.minorityReport);
  console.log("Open questions:", result.openQuestions);

// Never suppress warnings

The inspect command is free — it shows you exactly which seats would be selected and why, without making any API calls. Use it to understand routing before committing to a debate.

What Comes Next

Parliagent ships 33 production-grade seats, 4 debate modes, 3 execution profiles, 5 answer modes, 4 provider adapters (all live-validated), a CLI, an SDK, and a serverless adapter. 151 tests across 14 files. It works. The benchmarks are real. The limitations are documented.

Here are the genuine open questions — several surfaced by the parliament's own self-review:

  • Ground-truth validation: The parliament's sharpest critique of itself: we measure disagreement volume, not decision quality. The next step is comparing Parliagent outputs against human expert panels and tracking actual outcomes. Until then, we're honest that "more disagreements" is a proxy, not proof.
  • Multi-provider diversity: Federated mode is live-validated with Anthropic+OpenAI and FLOCK+Anthropic combinations — the plumbing works. The open question is whether cross-provider debates produce meaningfully different disagreements than single-provider runs.
  • Convergence tuning: 29/30 runs hitting the round limit suggests our convergence thresholds need work. Or maybe debates on hard problems shouldn't converge. We need more data to decide.
  • Deep mode: Implemented but not benchmarked. 7-13 seats across 3 rounds with a 60k token budget. We want to understand when this adds value over fast mode before recommending it.
  • Better routing: Keyword-based task classification works but misses subtlety. A security question framed as a business question won't trigger the security auto-upgrade. This needs a smarter classifier.
  • FLOCK as a universal adapter: The FLOCK provider's OpenAI-compatible interface means any LiteLLM-style proxy or custom endpoint could plug in. We want to explore this as a path to supporting dozens of model backends through a single adapter pattern.

The broader question — is structured multi-agent deliberation fundamentally better than single-agent reasoning for complex decisions? — doesn't have a clean answer yet. Our own parliament said as much. When we asked 33 seats to review this very article, every single one gave "mixed" — not "support." They found the architecture compelling but the evidence insufficient. They liked the honesty but wanted ground-truth validation. They thought the Nietzsche quote was memorable but worried it was gimmicky.

We're publishing their critique alongside our claims because that's the whole point: the tool that suppresses its own dissent has already failed.

Maybe structured disagreement isn't the final answer to AI reasoning. But it's a better starting question than confident agreement. Not every tool needs to be an oracle. Sometimes it just needs to be the one that asks what the oracle missed.
